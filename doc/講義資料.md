## 1. Git とは / GitHub とは

### Git とは

[https://git-scm.com](https://git-scm.com)

**ファイルの変更履歴を記録・管理するツール**（バージョン管理システム）です。自分のPCの中で動きます。

- ゲームの「セーブポイント」のように、好きなタイミングで状態を記録（コミット）できる
- いつでも過去の状態に戻せる・差分を確認できる
- `レポート_最終版_修正2_本当に最終.docx` のようなファイルを量産しなくてよくなる

Git で管理しているフォルダのことを **リポジトリ** と呼びます。
「プロジェクトのファイル」と「これまでの変更履歴（セーブデータ）」がまとめて入っているフォルダ、とイメージしてください。

### GitHub とは

[https://docs.github.com/ja/get-started/using-github/hello-world](https://docs.github.com/ja/get-started/using-github/hello-world)

**リポジトリ（ファイル＋変更履歴）をインターネット上に置いて、共有・共同作業できるサービス**です。

- チームでコードを共有する
- Pull Request（PR）でコードレビューをする
- ポートフォリオとして就活で見せる

> **Git ≠ GitHub**
> Git は「道具」、GitHub は Git を使うための「場所（サービス）」。
> 似たサービスに GitLab、Bitbucket などがあります。

### 用語

| 用語                     | 意味                                           |
| ------------------------ | ---------------------------------------------- |
| リポジトリ（repository） | 履歴付きのプロジェクトフォルダ                 |
| コミット（commit）       | 変更をセーブポイントとして記録すること         |
| ブランチ（branch）       | 作業の枝分かれ。本流(main)を壊さずに作業できる |
| リモート（remote）       | GitHub 上にあるリポジトリ                      |
| クローン（clone）        | リモートのリポジトリを自分のPCにコピーすること |
| プッシュ（push）         | 自分のPCのコミットを GitHub に送ること         |
| プル（pull）             | GitHub の最新の変更を自分のPCに取り込むこと    |
| プルリクエスト（PR）     | 「この変更を取り込んでください」というお願い   |

### GitHub を使うときの注意点 ⚠️

- **Public リポジトリは全世界に公開されます。** 削除しても、履歴やコピーが残ることがあります(clone,fork)
- **パスワード・APIキー・`.env` ファイル・個人情報は絶対にコミットしない**
  - うっかり公開した API キーは数分で悪用されることもあります
- コミットには**名前とメールアドレスが記録**されます
- アカウント名・公開しているコードは**就活で企業に見られる**ことがあります
- 学校の課題の答えを公開したり、他人のコードを無断でコピーして公開したりしないようにしてください。

## 5. 2要素認証（2FA）

GitHub ではアカウントログイン時に **2要素認証が必須** です。
パスワードに加えて、スマホで確認することで、パスワードが漏れても不正ログインされにくくなります。

### 方法A：認証アプリを使う（Google Authenticator / Microsoft Authenticator など）

1. **Settings** → **Password and authentication** → **Enable two-factor authentication**
2. 表示される QR コードを認証アプリで読み取る
3. アプリに表示される6桁のコードを入力
4. **リカバリーコードをダウンロードして保存**（とても重要）

### 方法B：よく分からない人は GitHub Mobile を使う

1. スマホに **GitHub Mobile** アプリをインストール（App Store / Google Play で「GitHub」）
2. アプリを開き、作ったアカウントでサインイン
3. PC で **Settings** → **Password and authentication** → **Enable two-factor authentication** を開き、画面の案内に従って設定する
   - 画面の指示に従い、認証アプリまたは SMS の設定を先に求められた場合はそれも行う
4. **リカバリーコードをダウンロードして保存**
5. 設定後、PCでログインすると GitHub Mobile に「承認しますか？」と通知が来るので **Approve** を押すだけでログインできるようになる

> ⚠️ **リカバリーコードは必ず保存！**
> スマホをなくしたり機種変更したりしたとき、これがないとアカウントに二度と入れなくなることがあります。
> PCとは別の場所（クラウドストレージなど）にも保管しましょう。

## 6. SSH キーの作成と登録

PC と GitHub の間を安全に通信するための「鍵」を作ります。

- **秘密鍵**（`id_ed25519`）… 自分のPCだけに置く。**絶対に人に渡さない**
- **公開鍵**（`id_ed25519.pub`）… GitHub に登録する

### SSH【Secure Shell】とは
- ネットワークを介して別のコンピューターやサーバーを安全に遠隔操作・管理するための通信規格（プロトコル）です。
- GitHubにSSH鍵を登録する理由は、「個人のパソコン」と「GitHub」の間で、安全かつ毎回パスワードを入力せずにデータのやり取り（プッシュやプル）を行えるようにするためです。


### 6-1. 鍵を作る（Windows は Git Bash で実行）

- 「GitHubに安全にログイン・接続するためのSSH鍵を、自分のPC上に作る」

```bash
ssh-keygen -t ed25519 -C "GitHubに登録したメールアドレス"
```

- 保存場所を聞かれたら **そのまま Enter**
- パスフレーズを聞かれたら、設定するか、空のまま Enter（2回）

```
~/.ssh/
├── 秘密鍵  id_ed25519
└── 公開鍵  id_ed25519.pub
```

### 6-2. 公開鍵の中身をコピー

```bash
cat ~/.ssh/id_ed25519.pub
```

`ssh-ed25519 AAAA....` から始まる1行を**すべて**コピーします。

> `.pub` が付いていない方（秘密鍵）は貼らないこと！

### 6-3. GitHub の「SSH keys」に登録

1. GitHub 右上アイコン → **Settings** → **SSH and GPG keys**
2. **New SSH key**
3. Title：`school-pc` など分かる名前
4. Key：コピーした公開鍵を貼り付け
5. **Add SSH key**

### 6-4. 接続確認

```bash
ssh -T git@github.com
```

初回は `Are you sure you want to continue connecting (yes/no)?` と聞かれるので `yes` と入力。

```
Hi ユーザー名! You've successfully authenticated, but GitHub does not provide shell access.
```

と表示されれば成功です 🎉

## 7. Git コマンドの使い方

- 自分のgithubリポジトリを作成して、コマンドの練習をしよう
  - https://github.com/自分のアカウント名


### 7-1. 全体像
- https://git-scm.com/book/ja/v2/%E4%BD%BF%E3%81%84%E5%A7%8B%E3%82%81%E3%82%8B-Git%E3%81%AE%E5%9F%BA%E6%9C%AC


- 3つの状態

```
 作業ツリー  ──add──▶  ステージ  ──commit──▶  ローカルリポジトリ  ──push──▶  GitHub
 (編集中)             (記録予定)              (自分のPCの履歴)            (リモート)
```

### 7-2. 基本コマンド

```bash
# リポジトリを自分のPCにコピー
git clone git@github.com:<オーナー>/<リポジトリ名>.git
cd <リポジトリ名>

# 今の状態を確認（困ったらまずこれ）
git status

# 変更をステージに追加
git add ファイル名
git add .            # すべての変更

# コミット（セーブポイントを作る）
git commit -m "何をしたかを書く"

# 履歴を見る
git log --oneline

# GitHub に送る
git push

# GitHub の最新を取り込む
git pull

# ブランチ
git branch               # 一覧
git checkout -b ブランチ名 # 新しくブランチを作成してそのブランチに移動
# git switch -c ブランチ名  # ↑と同じ
git checkout main          # main に移動
```

### 7-3. GitHub Desktop との対応

| やりたいこと | コマンド        | GitHub Desktop                                  |
| ------------ | --------------- | ----------------------------------------------- |
| clone        | `git clone ...` | File → Clone repository                         |
| 状態確認     | `git status`    | 左側の「Changes」タブ                           |
| add          | `git add`       | Changes のチェックボックス                      |
| commit       | `git commit -m` | 左下に Summary を書いて「Commit to ブランチ名」 |
| push         | `git push`      | 上部の「Push origin」                           |
| pull         | `git pull`      | 上部の「Fetch origin」→「Pull origin」          |
| ブランチ作成 | `git checkout -b` | 上部「Current branch」→「New branch」           |
| PR 作成      | （GitHub上で）  | Branch → Create pull request                    |

> まずコマンドで「何が起きているか」を理解し、普段は使いやすい方を使えばOKです。

```bash

cd git-practice-2026
git status
git log --oneline

```
HEAD =「今、自分がいる場所」

## 8. チーム開発で使う GitHub

### 8-1. なぜ main に直接 push しないのか

main は「いつでも動く完成品」の置き場です。全員が直接 main を書き換えると、誰かのミスが全員に影響します。
そこで **ブランチで作業 → PR でレビュー → OK なら main に取り込む** という流れにします。

### 8-2. ブランチ戦略（GitHub Flow）

```
main  ──●──────────────●───────────●──▶
         \            / (merge)   /
feature   ●──●──●────            /
                \               /
feature2         ●──●──●────────
```

1. main は常に動く状態に保つ
2. 作業ごとに main からブランチを作る（例：`feature/login`、`fix/typo`）
3. ブランチでコミット & push
4. Pull Request を作る
5. チームメンバーがレビュー
6. OK なら main にマージ → ブランチを削除

> 大規模な開発では develop / release / hotfix ブランチを使う **Git Flow** という戦略もあります。

### 8-3. Pull Request（PR）とは

「このブランチの変更を main に取り込んでください」というお願いです。PR 上で

- 変更内容（差分）の確認
- コメントでの質問・指摘
- 承認（Approve）

ができます。

### 8-4. PR 演習

- ブランチ作成 → ファイル追加 → commit → push → PR 作成


```bash
cd git-practice-2026
git branch main
git pull

# ブランチを作る
git checkout -b br_xxxxxx
```

#### ファイルを追加
practice/xxxxxx.md
- なにか一言、二言


```bash
git add 変更したファイル名
git commit -m "適切なコミットメッセージ"

git push -u origin ブランチ名
# -u　をつけるとpush先を指定して、今後のデフォルトとして記憶させる
# 以降はこのブランチにいる限り、 git pushのみれOKになる
```

GitHub の演習リポジトリを開くと **「Compare & pull request」** ボタンが出ているので押します。

- Title：`一言追加`
- Description：何を追加したか一言
- **Create pull request**

####　リポジトリ管理者

レビューして **Approve → Merge pull request**。全列の PR が main に取り込まれたら、全員で最新を取り込みます。

```bash
git checkout main
git pull
```

## 9. 一通りの流れ（まとめ）

```
git clone          … 最初に1回
  ↓
git checkout main
git pull           … 作業前に最新のmainを取り込む
  ↓
git checkout -b 作業ブランチ
  ↓
（コードを書く）
  ↓
git add → git commit    … 何度でも
  ↓
git push -u origin 作業ブランチ
  ↓
GitHub で PR 作成 → レビュー → マージ
  ↓
git checkout main → git pull   … 次の作業へ
```

### 困ったときは

- とりあえず `git status` を見る。次にやるべきことがヒントとして表示されていることが多い
- エラーメッセージをそのまま検索する
- 分からなくなったら、ファイルを消したりせずに、調べたり知っている人に聞く
